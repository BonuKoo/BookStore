# 재고 차감 동시성 전략 4종 실측 비교

같은 상품 한 행(hot row)에 "재고 1 차감"을 200회 수행하는 동일 워크로드를,
동일 하니스(`loadtest/lock_bench.py`)로 4가지 전략에 걸어 비교했다.
동시 실행 전략(1~3)은 40 스레드 경합, 큐 직렬화(4)는 단일 소비자 순차 처리.
각 전략 3라운드 실행 후 중앙값 채택, 매 라운드 최종 재고 == 초기 − 성공수 정합성 검증.

- 실행일: 2026-07-20, MySQL 8.0.41 (PC1 로컬), Python/pymysql 하니스
- 낙관적 락 재시도 상한 50회(지터 백오프 1~5ms), 비관적 락은 `SELECT ... FOR UPDATE`

## 결과 (중앙값)

| 전략 | 총 소요 | 처리량 | p95/건 | 재시도(충돌) | 요청 실패 | 정합성 |
|---|---:|---:|---:|---:|---:|---|
| 비관적 락 (`FOR UPDATE`) | 2,173ms | 92 ops/s | 743ms | 0 | 0 | ✅ |
| 낙관적 락 (`@Version` CAS+재시도) | 2,677ms | 72 ops/s | 987ms | **2,733** | **3~8건 (재시도 소진)** | ✅ |
| 원자 UPDATE (조건부, MQ 컨슈머 전략) | 1,639ms | 122 ops/s | 160ms | 0 | 0 | ✅ |
| 큐 직렬화 (단일 컨슈머 모델) | **425ms** | **470 ops/s** | **2.8ms** | 0 | 0 | ✅ |

> 원자 UPDATE의 3라운드 중 1회는 8.5초의 이상치가 관측됨(디스크 플러시/OS 스케줄링 추정) — 중앙값 채택으로 배제했으나 기록해 둔다.

## 해석

**1. 낙관적 락은 hot row 고경합의 최악 케이스다.**
200건 처리에 버전 충돌이 2,733회 — 요청당 평균 13.7회 재시도했고, 그마저도 3~8건은
상한(50회)을 소진하고 **실패**했다. 낙관적 락은 "충돌이 드물다"는 전제 위의 전략이므로,
모두가 같은 행을 쓰는 재고 차감에는 구조적으로 부적합함이 수치로 확인된다.
(읽기 위주/충돌 희소 환경에서는 여전히 유효한 선택.)

**2. 비관적 락은 정확하지만 대기가 길다.**
실패도 재시도도 없지만, 락 대기열에 줄을 서느라 p95가 743ms — 요청 하나가
사용자 체감 한계선까지 밀린다. 스레드가 늘수록 대기는 선형으로 악화된다.

**3. 조건부 원자 UPDATE가 동시 실행 중 최선.**
`UPDATE ... SET stock=stock-1 WHERE stock>=1`은 읽기-수정-쓰기 왕복 자체를 없애
행 락 점유 시간을 최소화한다. 같은 경합에서 비관적 락보다 25% 빠르고 p95는 1/4.
**이것이 분산 메시지 파이프라인의 재고 차감 컨슈머(`StockDeductionService` →
`ItemRepository.deductStock`)가 실제로 쓰는 전략이다.**

**4. 큐 직렬화는 경합을 "이기는" 게 아니라 "제거"한다.**
같은 200건을 단일 소비자가 순차 처리하면 425ms — 40 스레드 동시 실행의 어떤
전략보다도 3.8~6.3배 빠르다. 락 경합·재시도·대기가 모두 0이기 때문.
동시성 제어의 최적해가 "더 좋은 락"이 아니라 **아키텍처(직렬화)**일 수 있음을 보여준다.

## 분산 메시지 파이프라인과의 관계

이 프로젝트의 결제 확정 파이프라인은 위 표의 3+4를 결합한 형태다:

```
동기 API (경합 발생 지점)          비동기 파이프라인 (경합 제거)
confirm API ──publish──▶ RabbitMQ큐 ──단일 컨슈머──▶ 원자 UPDATE + 멱등 가드
                          (직렬화)     (queue-serial)   (atomic, at-least-once 대비)
```

- 큐가 요청을 직렬화해 **행 경합 자체를 제거**하고 (표의 queue-serial),
- 컨슈머는 그래도 조건부 원자 UPDATE를 사용해 **컨슈머 증설(경쟁 소비)이나
  중복 전달(at-least-once) 상황에서도 안전**하며 (표의 atomic),
- `stock_deduction(order_id UNIQUE)` 멱등 가드가 재전달 중복 차감을 차단한다.

트레이드오프: 사용자는 차감 완료를 동기로 확인하지 못하고(비동기 완결 통지),
브로커 홉만큼의 지연이 추가된다. 즉 "빠른 개별 응답"을 포기하고
"경합 없는 총처리량 + 유실/중복 없는 보장"을 얻는 구조.

## 방법론의 한계 (정직성 노트)

- 하니스는 Python/pymysql — JPA 프록시·영속성 컨텍스트 오버헤드가 없으므로
  **절대 수치는 Spring 운영 코드와 다르다.** 단 4전략 모두 같은 하니스를 통과하므로
  전략 간 **상대 비교는 공정**하다. 각 전략의 SQL은 JPA가 발행하는 것과 동일
  (`FOR UPDATE` / version CAS / 조건부 UPDATE).
- 별도로 Spring 레벨 검증도 존재: 낙관적 락 + 재시도 파사드를 200 동시 스레드로
  검증하는 `@SpringBootTest`(feat.checkout-lock-dev 브랜치,
  `OptimisticLockStockFacadeTest`)가 락 충돌 시스템 오류 0건·재고 정합성을 확인했다.
  비관적 락의 Spring 테스트는 프로토타입 단계에서 중단된 상태(주석 처리)로,
  본 벤치마크가 그 공백을 하니스 레벨에서 메운다.
- queue-serial 수치는 DB 직렬화 이득만 측정한 것 — 실제 MQ 경유 시 브로커 홉,
  발행/ack 오버헤드가 건당 수 ms 추가된다(실측: Phase 5 실험에서 ledger-worker가
  원격 MySQL 쓰기 포함 건당 ~43ms).
