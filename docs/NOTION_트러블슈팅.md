## 1. 주문 생성 시 N+1 쿼리 폭발

**문제**
장바구니 N개 항목으로 주문을 만들 때, 항목 수에 비례해 SELECT가 늘어남. 상품 6개 주문 시 상품 조회만 6번 추가 발생.

**원인**
`cartItemRepository.findAllById()`로 CartItem만 조회한 뒤, 루프에서 `cartItem.getItem().getPrice()` 접근 → LAZY 연관관계가 항목마다 개별 SELECT를 유발. 구매자 정보도 `getCart().getAccount()` 체인으로 2회 추가 조회.

**해결 (2단계)**
1. QueryDSL `fetchJoin()`으로 CartItem+Item을 한 번에 로딩 → N+1 제거
2. 한 단계 더: 화면·주문 생성에 필요한 컬럼만 뽑는 **DTO 프로젝션**(`@QueryProjection`)으로 전환 → 엔티티 로딩 자체를 제거해 영속성 컨텍스트 관리 비용과 페이로드까지 절감

**배운 점**
"조회 결과로 무엇을 하는가"에 따라 fetch join(엔티티가 필요할 때)과 프로젝션(값만 필요할 때)을 구분해야 한다. p6spy로 실행 SQL을 눈으로 확인하는 습관이 최적화의 출발점.

## 2. 동시 주문 중복 생성 — check-then-insert의 함정

**문제**
같은 사용자가 주문 버튼을 연타하거나 네트워크 재시도가 겹치면 동일 주문이 2건 생성됨. "사전 조회 후 없으면 저장" 로직이 있는데도 발생.

**원인**
`SELECT(존재 확인) → INSERT` 사이의 시간 창에서 두 트랜잭션이 모두 "없음"을 보고 각각 INSERT — 전형적인 **check-then-act race condition**. 애플리케이션 레벨 조회로는 원천 차단 불가.

**해결**
- 멱등성 키 도입: `UUID.nameUUIDFromBytes(userId + 정렬된 cartItemIds)` → `order_id` **UNIQUE 제약**
  - 항목 순서가 달라도 같은 키가 나오도록 정렬 후 해싱
- 전략 전환: 사전 조회를 없애고 **일단 INSERT → 중복키 예외(DataIntegrityViolationException)를 catch** → 기존 주문을 조회해 `409 + 동일 orderId` 반환
- DB의 유니크 제약이 동시성의 최종 심판자가 되므로 race 자체가 불가능

**과정에서 추가로 겪은 문제**
- 중복키 예외 발생 후 **같은 트랜잭션에서 기존 주문을 조회하면 롤백 마킹 때문에 실패** → 조회를 `REQUIRES_NEW` 트랜잭션으로 분리한 별도 서비스로 해결
- 실패한 엔티티가 영속성 컨텍스트에 남아 이후 동작을 오염 → 분리 트랜잭션 + 필요한 컬럼만 뽑는 프로젝션 조회로 회피

**배운 점**
동시성 제어의 마지막 보루는 애플리케이션 코드가 아니라 DB 제약이다. 그리고 예외 이후의 "복구 조회"는 트랜잭션 경계를 반드시 따져야 한다.

## 3. 운영 체크아웃 100% 실패 — 엔티티와 실제 스키마의 불일치

**문제**
E2E 테스트에서 주문 생성이 무조건 실패. 코드 리뷰 단계에서 "이 경로는 항상 깨질 것"이라 예측했던 지점이 실측으로 확인됨.

**원인**
`payment_event.buyer` 컬럼이 실제 스키마에서 **NOT NULL**인데, 운영 `CheckoutService`는 `buyerId`(단순 Long 컬럼)만 세팅하고 FK 연관관계(`accountEntity`)를 비워둔 채 INSERT. `ddl-auto: none` 환경이라 코드(엔티티 정의)와 실제 DB가 조용히 어긋나 있었음.

**해결**
주문 생성 조회를 `customCartItemProjection2`(구매자 AccountEntity 포함 프로젝션)로 교체하고 PaymentEvent 빌드 시 `accountEntity`를 세팅. E2E 전 구간 통과 확인.

**배운 점**
`ddl-auto: none`이면 엔티티 정의는 스키마의 "희망사항"일 뿐이다. 마이그레이션 도구(Flyway/Liquibase) 없이 수동 관리되는 스키마는 이런 불일치를 만든다. 그리고 `buyerId`/`accountEntity` 같은 이중 표현은 결국 한쪽이 잊힌다.

## 4. 토스 결제위젯이 키를 거부 — "키에도 종류가 있다"

**문제**
결제위젯 SDK 초기화 시 `결제위젯 연동 키의 클라이언트 키로 SDK를 연동해주세요. API 개별 연동 키는 지원하지 않습니다.` 오류.

**원인**
토스페이먼츠의 클라이언트 키는 **API 개별 연동 키(test_ck_)** 와 **결제위젯 연동 키(test_gck_)** 로 나뉘며 SDK가 요구하는 종류가 다름. 설정 파일에 두 계열 키가 혼재되어 있었고, 승인(confirm)에 쓰는 시크릿 키는 위젯 계열(test_gsk_)이었음.

**해결**
프론트의 클라이언트 키를 confirm 시크릿과 **같은 쌍의 위젯 키(test_gck_)** 로 통일. 클라이언트 키 ↔ 시크릿 키는 반드시 같은 연동 방식의 페어여야 승인까지 이어진다.

**배운 점**
외부 PSP 연동은 "키 페어 관리"부터가 설계다. 설정 파일에 어떤 연동 방식의 키인지 주석으로 명시해 두어야 한다.

## 5. `@Async` 메서드의 예외가 증발 — 죽은 catch 블록

**문제**
낙관적 락 재고 감소를 `@Async void` 메서드로 만들고 호출부에서 재고 부족/락 충돌을 try-catch로 분기했는데, **catch가 한 번도 실행되지 않음**. 재고 감소가 끝나기 전에 주문 저장이 진행되는 순서 문제도 발생.

**원인**
`@Async void`는 호출 즉시 리턴하고 별도 스레드에서 실행된다. 예외는 호출자에게 전파되지 않고 `AsyncUncaughtExceptionHandler`로 사라짐 → 호출부의 catch는 도달 불가능한 죽은 코드.

**해결**
`CompletableFuture<Void>`를 반환하도록 변경하고, 실패는 `CompletableFuture.failedFuture(e)`로 담아 전달. 호출부는 `allOf(...).join()`으로 완료를 대기하고 `CompletionException`에서 원인 예외를 꺼내 분기. 재고 감소 완료 → 주문 저장 순서도 보장됨.

**배운 점**
비동기 전환은 "메서드에 어노테이션 붙이기"가 아니라 **예외 전파 경로와 완료 시점 보장**을 다시 설계하는 일이다.

## 6. 낙관적 락 재시도 폭주 — 백오프 튜닝

**문제**
재고 경합이 심할 때 락 충돌 재시도가 몰리며 응답이 수 초까지 늘어지고, 재시도끼리 다시 충돌하는 악순환.

**해결**
- **지수 백오프**: `10ms × 2^attempt`, 단 상한 캡(100ms)으로 폭주 방지
- 사용자 대면 경로는 재시도 횟수를 100회 → 5회로 축소해 "빠른 실패 + 안내 메시지"로 전환 (최대 대기 ~250ms 목표)
- 복구(보상) 경로는 반대로 재시도를 넉넉히 — 사용자 응답과 무관하고 데이터 정합성이 우선이므로
- `InterruptedException` 발생 시 `Thread.currentThread().interrupt()`로 인터럽트 상태 복원

**배운 점**
재시도 정책은 하나가 아니다. **사용자 경로(빨리 실패)와 정합성 경로(끝까지 복구)는 다른 파라미터**를 가져야 한다.

## 7. JWT 파싱 객체를 매 요청 생성 — GC 부하

**문제**
부하 테스트 중 인증 필터 구간에서 불필요한 객체 생성과 GC 오버헤드 확인.

**원인**
요청마다 `Jwts.parserBuilder()...build()`로 `JwtParser`를 새로 조립. 서명 키 객체도 반복 생성.

**해결**
`JwtParser`를 `@Configuration`에서 싱글톤 빈으로 한 번만 생성해 주입. 서명 키도 생성자에서 1회 초기화.

**배운 점**
필터는 모든 요청이 지나는 길목이라 작은 낭비도 부하 시 증폭된다. "요청당 생성 객체"를 의심하는 것이 프로파일링의 첫 질문.

## 8. 감사 이력에 `PaymentFailure@67943a54` — toString 미구현

**문제**
결제 실패 이력의 사유(reason) 컬럼에 사람이 읽을 수 없는 객체 해시가 저장됨.

**원인**
이력 기록 시 `failure.toString()`을 그대로 저장하는데 `PaymentFailure`에 `toString()` 미구현 → `Object.toString()` 기본값이 기록됨.

**해결/교훈**
`errorCode + message` 포맷으로 명시 직렬화. **감사 로그는 저장 시점이 아니라 "나중에 읽는 시점"을 위해 존재**한다 — 기록 코드를 짤 때 읽는 사람 입장에서 검증할 것.

## 9. (Frontend) 백엔드가 미인증을 403으로 — 세션 만료와 비즈니스 403의 충돌

**문제**
토큰 만료 시 401이 아닌 **빈 본문 403**이 내려옴. 그런데 중복 주문 응답도 403(+본문)이라, "403이면 로그인으로" 규칙을 그대로 쓰면 정상 비즈니스 응답까지 로그아웃 처리됨.

**해결**
Axios 인터셉터에서 **본문 유무로 구분**: 본문 없는 403 → 인증 실패(토큰 제거 후 로그인 이동), 본문 있는 403 → 비즈니스 응답으로 통과. 근본 해결은 백엔드가 401/403을 표준대로 구분하는 것(개선 백로그에 등록).

## 10. (Frontend) 수량 변경 API가 "가산"이 아니라 "덮어쓰기"

**문제**
increase/decrease 두 엔드포인트가 있지만 실제 동작은 모두 전달한 값으로 **수량을 대입**. +1 의도로 1을 보내면 수량이 1이 되어버림.

**해결**
프론트에서 현재 수량 기준 **최종 수량(absolute)** 을 계산해 전송하는 단일 함수(`setCartItemAmount`)로 래핑. API 이름과 실제 시맨틱이 다를 수 있으므로, 연동 전에 백엔드 구현을 직접 읽고 계약을 문서화하는 것이 안전하다.
