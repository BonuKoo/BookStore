## 1. 주문 생성 조회 최적화 — N+1 → fetch join → DTO 프로젝션

주문 상품 **N개** 기준, 주문 생성 1회의 SELECT 수 (코드 기준 산출):

| 버전 | 조회 방식 | SELECT 수 | 비고 |
| --- | --- | --- | --- |
| v1 | `findAllById` + LAZY 접근 | **3 + N** | 사전조회 1 + CartItem 1 + Item N + Account 경유 1~2 |
| v2 | QueryDSL `fetchJoin` | **2~3** | 사전조회 1 + (CartItem⋈Item) 1 + Account 경유 |
| v3 | DTO 프로젝션 (`@QueryProjection`) | **2** | 사전조회 1 + 필요한 컬럼만 단일 쿼리 |
| v4 | 중복-사전조회도 프로젝션화 | **2** | 중복 검사 쿼리의 로딩 범위 축소 (컬럼 3개) |
| v6+ | **사전조회 제거** (unique key + catch) | **1** | 성공 경로 SELECT 1회 — 중복일 때만 +1 |

| --- | --- | --- | --- |
| v1 (N+1) | [측정값] | [측정값] | [측정값] |
| v3 (프로젝션) | [측정값] | [측정값] | [측정값] |

## 2. 중복 주문 처리 — 사전 조회 제거의 효과

| | Before (check-then-insert) | After (insert-then-catch) |
| --- | --- | --- |
| 정상 주문(대부분의 트래픽) | SELECT + INSERT | **INSERT만** |
| 중복 주문(드문 케이스) | SELECT + (race 시 중복 생성 💥) | INSERT 실패 → SELECT 1회 |
| 동시성 안전 | ❌ race window 존재 | ✅ DB UNIQUE가 최종 보장 |
| 응답 의미 | 불명확 | 200 신규 / 409 기존(동일 orderId) |

**설계 판단**: 흔한 경로(신규 주문)를 최적화하고, 드문 경로(중복)에 비용을 지불하는 구조로 전환. 멱등성 보장과 쿼리 절감을 동시에 달성.

## 4. 쓰기 처리량 — JPA 배치 설정

| 설정 | 값 | 효과 |
| --- | --- | --- |
| `hibernate.jdbc.batch_size` | 1000 | 다건 INSERT를 배치로 묶어 왕복 감소 |
| `order_inserts` / `order_updates` | true | 같은 테이블 문장을 모아 배치 효율 확보 |
| 시딩 처리량 | Spring Batch chunk 100~1000 | 4,200만 건 상품 적재에 사용 |

> ⚠️ 확인된 한계: PK가 IDENTITY 전략이면 Hibernate가 INSERT 배치를 비활성화한다. 시퀀스/테이블 제너레이터(allocationSize) 전환 실험 흔적을 코드에 보존 — 현재는 MySQL 특성상 IDENTITY 유지, 대량 적재는 Batch가 담당.
